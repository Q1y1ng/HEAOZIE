# 夜间工作报告 · 2048 4×4 引擎（2026-10-25 02:00–06:30）

> 起点：`engine.cpp`（数组棋盘 + 手工线性特征）100 ms/步 均分 37.6k、最高 60.8k（4096）。
> 终点：`engine_bb.cpp`（bitboard + 概率截断）**18 局均分 231.9k、最高 387.4k（16384）、16384 率 39%**；
> 顺带验证 **5×5 在深度 3.2 下就能 4/5 上 16384（均分 341k）**。

## 0. 一句话

把棋盘压进一个 `uint64_t` + 行查表 + 置换表 + 概率截断，单核从 0.4 M 节点/s 提到 **13–18 M 节点/s**、
深度从 4.5 提到 6.0，同样 100 ms/步：**18 局均分 231.9k（旧引擎 37.6k，6.2 倍）**、
最高 **387.4k（16384）**、16384 率 **39%**、8192 及以上 **94%**。
再往上（32768）已经不是搜索速度问题——**评估函数才是天花板**，两个"加深"实验都失败了。
顺带：**5×5 用深度 3.2 的旧数组引擎就打出 833,740 分 / 32768 块**（6 局均分 423k，16384 及以上 5/6）
——棋盘越大越宽容，4×4 至今没拿到的 32768 在 5×5 上顺手就有了。

## 2. 引擎怎么做的（`nn2048/engine_bb.cpp`，约 800 行）

| 模块 | 做法 | 效果 |
| --- | --- | --- |
| 棋盘 | `uint64_t`，16 格 × 4 bit 存 log2（0 空、1=2、…、15=32768） | 移动/比较/TT 键都是单条 64 位指令 |
| 移动 | 65536 项行表（左/右，含得分）；上/下 = 转置后走左/右再转置回来；一次四方向决策共享 **1 次**棋盘转置（共 3 次） | 一次移动 4 次查表 |
| 评估 | 行表：行内 `sum^3.5`、单调性 `^4`、合并段数、空格数，权重 270/47/11/700；棋盘分 = 4 行 + 转置后 4 列 = 8 次查表 | 热路径无 `pow`/`min` |
| 搜索 | 期望最大；max 节点 → chance 节点（全部空格、2/4 按 0.9/0.1） | 真实规则，2 与 4 都算 |
| 剪枝 | **概率截断**：累计 spawn 概率 < 1e-4 的分支直接静态评估 | 自适应深度：开局 ×14/层（3 层就截断），残局 ×4/层（能搜 8–10 层） |
| TT | 直映射 2^22 槽 × 16 B，键=整块棋盘 + 深度；只写"干净值"（子树内没发生概率截断的） | 命中率 **75–77%** |
| 根 | 迭代加深 + 着法排序 + 时间预算；超时的那一层**只保留已完成着法的较优值** | 少浪费 20–40% 预算 |
| 自检 | `--selftest` 对拍 | 表或搜索语义一改就报错 |
| 平台 | 启动时 `SetProcessInformation(ProcessPowerThrottling)` 退出 Windows 后台节流 | 后台批次不再白丢一半算力 |

**6 局均分 423,247、16384 及以上 5/6、32768 1/6**——而深度只有 **3.2**
（数组引擎 0.4 M 节点/s，是 4×4 bitboard 的 1/40）。
棋盘一大，"活着"容易得多：同样的评估函数，5×5 用 4×4 三分之一的深度，
既拿到了 4×4 至今没拿到的 **32768**，均分还高出 80%。
这直接说明 5×5 的上限远高于 4×4，也说明**值得给 5×5 写一个 bitboard 引擎**
（25 格 × 4 bit = 100 bit，需要 `__uint128_t`；今晚没做）。

## 4. 三个教训

1. **深度 ≠ 强度。** 搜索里忽略 10% 概率的 4 号块后，平均深度从 5.31 涨到 6.05，
   均分却从 126k 掉到 64k（最差一局只到 512）。少算真实的概率分布 = 用深度换幻觉。
2. **6 局样本测不出 2 倍以内的差异。** 权重扫描第一批显示"空格权重 400 让均分涨 1.9 倍"，
   换一批种子复验后差异完全消失（235k vs 223k，差 12k < 标准误 33k）。
   以后任何权重实验 **≥20 局/臂 + 换种子复验**。
3. **后台进程会被 Windows 节流。** 隐藏控制台的引擎只有前台 ~55% 的算力，
   同样的 100 ms 预算只能跑到一半深度——引擎里已显式退出 EcoQoS。

## 6. 想上 32768，还差什么

- 32768 需要 **25,000 步以上**不犯致命错误；现在 16384 局平均 12,800 步就死，
  死在"只差一条链"的阶段——典型的评估函数问题：它分不清"再撑 3 步会死"和"还能再撑 30 步"。
- 三条可选路：
  1. **学习型评估**（n-tuple TD / 小 CNN）——论文水平均分 60 万、32768 70%，代价是几小时训练；
  2. **更深的搜索**（深度 8+）——今晚证明单纯加预算/加深没有收益，除非评估精度先上去；
  3. **专门的残局求解**（空格 ≤4 时搜到死亡）——只能治标，且算力开销大。
- 结论：**先做学习型评估**（`NN_PLAN.md` 的路线），用现在的 bitboard 引擎当 self-play 数据源
  （`bench_env.py` 已实测 39 万 moves/s），评估训好后直接替换 `evaluate()` 即可。
